Section A · five math bugs

The text computes the wrong thing as written

These are not stylistic. A careful reviewer — or a reader re-implementing the method — gets a different algorithm than the one we actually ran.

A1Eq. (6)'s ∞ case tests the wrong point

owner: [T] — inside Tal's Aug-3 equation · pending

what it says today
C*(d,t) = min … { ∞  if t̃ = tΘ , d < dM ; … }
why the change is needed

The ∞ case is meant to kill dead-end legs: those that land on the final time line without finishing the voyage. But the condition tests d — the source. Every state that has successors satisfies d < dM (only the destination doesn't, and it emits no arcs). So the condition is always true, and the case fires for every leg that touches the final time line.

Watch it break: T = 280 h. The vessel stands at (3,380 NM, 276 h) and a candidate leg arrives exactly at (L, 280) — destination, on the deadline, perfectly legal. The equation as written prices this leg ∞ and declares the voyage impossible on that path. The algorithm (line 11 seeds C*(L, t) = 0 for every t ≤ T, including t = T) and the code both accept it. Equation and algorithm currently disagree about which voyages are feasible.

the fix

One tilde: d̃ < dM — test the successor. "If the leg lands on the last time line short of the destination, it is a dead end."

A2The cell-lookup maps pick the rectangle behind the ship

owner: [T] — §4.1 definitions · pending

what it says today
i(d) = argmaxi{ di < d } ,   j(t) = argmaxj{ tj < t }  (strict) — then φ(d,t;v) uses the rectangle of (d̲, t̲) = (di(d), tj(t))
why the change is needed

The map is supposed to answer "which weather cell and which forecast block does this point's outgoing leg live in?" With a strict inequality, a point sitting exactly on a line — and every DP state sits on a line by construction — selects the region before the line, i.e. behind the ship, while the leg being priced travels ahead.

Watch it break: a state at t = 6.0 h exactly (a block boundary). The leg that starts there sails in block 1 (6–12 h, the new forecast). But {tj < 6.0} picks t0 = 0, so φ prices the leg with block 0's weather — the forecast that just expired. Same story in distance: a state on a cell boundary prices its leg with the cell it is leaving. Since all states live on lines, this misprices legs systematically — the code does the right thing; the definition doesn't.

the fix

Weak inequalities: di ≤ d and tj ≤ t. A point on a boundary then belongs to the rectangle ahead — the one its leg actually traverses.

A3The solution-prose still speaks "to-arrive"

owner: [T] — §4.1 prose after Eq. (6) · pending

what it says today
"The value of this solution is the minimum fuel to arrive on time at each state (d,t) … The SOG at the subsegment that starts at (d,t) is …"
why the change is needed

The sentence describes the old quantity. Under the cost-to-go flip, C*(d,t) is the fuel from (d,t) to the destination — not the fuel to reach (d,t). A reader who takes the sentence literally cannot reconcile it with the equation right above it: under the "arrive at" reading, C*(0,0) would be trivially 0 — yet the paper reads the answer there. The two statements contradict on the same half-page.

Second, smaller: the thing that starts at (d,t) is a leg (an arc of adaptive length), not a subsegment (a fixed piece of the route between cell boundaries). Using the reserved word blurs two defined objects.

the fix

"…the minimum fuel required to complete the voyage from (d,t) while meeting the ETA, or ∞ if the ETA cannot be met from there. The SOG of the leg that starts at (d,t) is …"

A4The soft-ETA remark charged a fee no one can incur

owner: [A] — §4.2 · ✔ RESOLVED in the flat rewrite

what it said
"Replacing the ∞ case with a lateness charge λ(t̃ − T) turns the hard deadline into a soft one…"
why the change was needed

On the grid, no arc ever lands past T — the time lines stop there, so t̃ ≤ T always, and the "charge" λ(t̃ − T) is never positive. The remark promised a soft deadline while describing a model in which lateness cannot even be expressed. A reviewer testing the throwaway remark finds it does nothing — worse than not saying it.

the fix (applied)

"Extending the time lines beyond T and replacing the ∞ case with a lateness charge λ·max(0, t̃ − T)…" — first make late arrivals representable, then price them.

A5"…the following forward Bellman equation"

owner: [T] — §4.1, the sentence introducing Eq. (6) · pending

why the change is needed

One stale word, but it points the reader in exactly the wrong direction: the recursion that follows is a cost-to-go, evaluated backwards from the destination. "Forward" was correct for the old to-arrive version and survived the flip. Whoever trusts the adjective will try to sweep the recursion forward — and it cannot be (a state's value needs its successors, which forward order hasn't visited yet).

the fix

Drop the adjective (or write "backward"): "…can be formulated as the following Bellman equation."

Section B · seven symbol collisions

One letter, two meanings

None of these makes the math false — they make it ambiguous. The damage is to the reader, who must guess which meaning is live at each occurrence; reviewers flag these mercilessly.

B1𝒜 is both the neighbour set and the arc accumulator

owner: [T/A] — one token of Tal's Algorithm-1 line 1 · pending

the two meanings, four lines apart
line 4:  C ← 𝒜(d,t) of Eq. (5) — the neighbour function: a set of states
line 7:  𝒜 ← 𝒜 ∪ {(d,t)→(d̃,t̃)…} — the arc set being built: a set of edges
why the change is needed

A careful reader of the box hits line 7 and asks: "are we inserting arcs into the neighbour set we just queried on line 4?" The two objects even have different types (states vs edges). The ambiguity leaks into Eq. (9), where |𝒜| means the arc count, and into the prose "(𝒮,𝒜) is acyclic". Every occurrence forces the reader to disambiguate from context.

the fix

Rename the accumulator to ℰ (edges): lines 1, 7, 13; |𝒜| → |ℰ| in Eq. (9); "(𝒮,ℰ)" in the sweep prose. Eq. (5)'s 𝒜(d,t) — Tal's — stays untouched.

B2g is both the SOG-inversion map and the slide gain

owner: [A] — §4.3 · pending

the two meanings
§3:  Vs = g−1(Vg; w) — the physics map SOG → required SWS
§4.3:  g(qk) = […] − min […] — Eq. (10): the fuel gain from sliding point qk
why the change is needed

Both live in the same Methods section, and §4.3's legs are priced through the §3 physics — so both g's are genuinely in scope at once. "g(qk)" invites the misreading "the SOG-map applied to the point qk", which is a perfectly plausible object in this paper.

the fix

Rename the gain to γ(qk) in Eq. (10) and its surrounding text (and in tab:certificate's caption if referenced). The physics keeps g−1.

B3di is a leg length in §3 and a cumulative breakpoint in §4

owner: [A] — §3 (eq:legfuel, eq:obj) · pending

the two meanings
§3:  Fi = FCR(…)·di/Vg,i — di = the length of leg i
§4:  di = di−1 + li, dM = L — di = distance from departure to breakpoint i
why the change is needed

These are the paper's two most-used distance symbols and they contradict across a section boundary. A reader who carries §4's (correct, grid-defining) meaning back into §3's objective gets Σ di/Vg,i = a sum of cumulative distances over speeds — a meaningless "travel time" that grows quadratically with route position. §4 also already reserves li for exactly the length concept §3 wants.

the fix

§3 switches to li: Fi = FCR(·)·li/Vg,i, constraint Σ li/Vg,i ≤ T. One symbol, one meaning, both sections agree.

B4M is used in §3 before anything defines it

owner: [A] — §3, eq:obj · pending

why the change is needed

The objective sums i = 1…M, but M (the number of subsegments/legs) is only defined a section later, in §4's preprocessing paragraph. The very first display equation of the formulation contains an unbound symbol — the kind of thing a referee circles on page one.

the fix

One clause before eq:obj: "…the voyage divides into M such legs (Section 4 makes the decomposition precise); leg i has length li…"

B5n means three different counts

owner: [A] — tab:certificate header · pending

the three meanings
Eqs. (4)–(5):  n = the grid-offset counter (0, 1, 2, … steps back from a line)
§4.3 text:  q0 … qn = the decision points of a schedule (~200)
tab:certificate:  column "n" = 7 and 12 — the number of voyages per route
why the change is needed

The dangerous pair is the last two: table and text sit in the same subsection. A reader who just met "q0…qn" naturally reads the table's n = 7 as "seven decision points per schedule" — wildly wrong (there are ~200), and it silently corrupts their reading of the recovered-percentage columns.

the fix

Rename the table column to "Voyages". The two remaining n's live in different subsections with clear local scope — acceptable.

B6L — the paper's most important constant — is never defined

owner: [T/A] — §4 intro, first use · pending

why the change is needed

L first appears silently inside "d ∈ [0, L]" and later as "dM = L". Its meaning (total route length, NM) is guessable — which is exactly why it was never caught. But "the reader can guess" is not a definition, and L appears in the size bound, the tractability numbers, the algorithm's termination test, and the boundary condition.

the fix

Three words at first use: "…along-track distance d ∈ [0, L] (L the total route length, NM)…"

B7κ appeared before its definition — and meant two things

owner: [A] — §4.2 · ✔ RESOLVED in the flat rewrite

why the change was needed

The walkthrough said "a state typically has κ ≈ 8 candidates" pages before κ was defined — and when the definition arrived, it defined κ as an upper bound ("at most κ arcs"), not a typical count. Same letter, undefined at first use, then subtly different semantics.

the fix (applied)

First mention now says "about eight such candidates (the count is bounded at the end of this section)"; κ enters exactly once, at the bound that defines it.

Section C · ten precision items

Imprecise, stale, or undefined

C1Two different grids: anchored (Eq. 4) vs absolute (the snap operator)

owner: [T] — a design question for the meeting, not a unilateral fix

the two definitions
Eq. (4):  grid points at di − nδ — anchored at each line crossing, stepping backward
§4.2:  ⟨x⟩δ := δ·round(x/δ) — absolute multiples of δ, anchored at zero
why this needs a decision

The distance-line positions di are cumulative route distances — generally not whole numbers of NM. So the two grids genuinely differ. Example: di = 137.4 NM, δ = 1. Eq. (4)'s points on the time line: 137.4, 136.4, 135.4, … The snap operator's points: 137, 136, 135, … Every point differs by 0.4 NM. Which set is 𝒮? The equation says one thing, the enumeration arithmetic (and the code, which works on integer NM) says the other. (Time is safe: the tj are multiples of 0.1 h, so the two coincide — this is a distance-axis-only question.)

the two candidate resolutions

(i) state that the di are pre-snapped to the δ-grid in preprocessing (then anchored = absolute and nothing else changes), or (ii) define the snap relative to the anchor. Tal's call — it is his grid construction.

C2"every τ-multiple" — the words said absolute, the grid is anchored

owner: [A] — §4.2 prose · ✔ RESOLVED in the flat rewrite

why the change was needed

Same subtlety as C1, but in prose: "every τ-multiple in the range" describes absolute multiples, while Eq. (4) anchors points at the crossings. The words now say "every τ-spaced grid point" — agnostic about the anchor, correct under either C1 resolution.

C3argmin of a membership predicate

owner: [T] — §4.1 · pending

what it says today
𝒟(d) = argmini { i ∈ ℕ : di > d }
why the change is needed

{ i : di > d } is a set of indices, not a function to minimise — "argmin of a set" is nonstandard notation that makes formally-minded reviewers stumble on an otherwise trivial definition. The intended object is simply the smallest element.

the fix

𝒟(d) = min{ i : di > d } — same for 𝒯(t), i(d), j(t) (the latter two with ≤ per A2).

C4"held constant across the rectangular sub-space" — but glide legs cross two

owner: [T] — §4.1 · pending (ties to standing prep item 3a)

why the change is needed

The sentence promises every leg lives inside one rectangle. The glide rule — needed when a distance wall is closer than vmaxτ — deliberately lets a leg pass through a skipped wall, crossing two cells while φ is evaluated only at the source. §4.2 states this honestly ("up to this boundary rule"); §4.1's sentence doesn't carry the caveat, so the two sections make different promises about the same legs.

the fix

Add the same qualifier used in §4.2 (or resolve item 3a by extending Eq. (5) with the corner case — Tal's standing decision).

C10φ is never formally tied to §3's physics

owner: [A] — one sentence after Tal's φ definition · pending

the missing identity
φ(d,t;v)  =  FCR( g−1(v; w(d,t)) ) — "the burn rate at SOG v is the cubic FCR of the still-water speed that achieves v in this cell's weather"
why the change is needed

§3 builds the physics chain SOG → required SWS → FCR; §4 introduces φ(d,t;v) as "the FCR at speed v in this rectangle" — and never says they are the same function. The link is obvious to us and invisible to a first-time reader; without it, §4's optimisation could be running on any burn model whatsoever. One identity closes the §3→§4 seam.
